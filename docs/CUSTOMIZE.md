# カスタマイズガイド

> **この文書の役割：サンプルを自分のアプリへ作り替える**
>
> 初回セットアップが終わったあと、サンプルの `items` を自分の業務・用途へ置き換えるための実装ガイドです。DB、業務処理、URL/API、画面、テストをどの順番で変更するかを扱います。
>
> **前の段階**：リポジトリ作成・Clone・初回起動がまだなら [新規開発スタートガイド](GETTING-STARTED.md)
>
> **別の話**：Commit / Push / CI / Pull / Releaseなどの運用は [開発・CI・ローカル反映・デプロイ運用](DEVELOPMENT-DEPLOYMENT.md)

基本方針は、**Python・SQLite・Tailscale・セキュリティなどの共通基盤を残し、サンプル `items` の業務部分を置き換える**ことです。

---

## 1. まず「何を置き換えるか」を理解する

テンプレートは大きく2つに分けて考えます。

```text
残す共通基盤
  auth.py / csrf.py / security.py / run.py など
  認証・認可 / localhost限定 / Tailscale / CSRF / セキュリティ

        ＋

自分用へ置き換える業務部分
  schema.sql / services/items.py / routes.py / templates / static / tests
```

主な変更対象は次のとおりです。

| ファイル・場所 | 変更する内容 |
| --- | --- |
| `.env` | アプリ名など環境設定 |
| `app/schema.sql` | 保存するデータ・テーブル |
| `app/services/items.py` | 登録・取得・更新・削除などの業務処理 |
| `app/routes.py` | 画面URL・API |
| `app/templates/` | HTML画面 |
| `app/static/` | CSS・JavaScript |
| `tests/` | 自分の機能に合わせた自動テスト |

---

## 2. 最初にアプリのデータモデルを決める

たとえば備品管理なら、サンプルの `items` を `equipment` と考え、必要な項目を決めます。

```text
備品ID
備品名
カテゴリ
保管場所
数量
備考
所有者
登録日時
更新日時
```

この時点で、次も決めます。

- 利用者ごとにデータを分離するか
- 複数利用者で共有するデータがあるか
- 誰が登録・編集・削除できるか

「ログインできる人」と「何を操作できるか」は別なので、必要ならアプリ側の権限制御も設計します。

---

## 3. アプリ名・環境設定を変更する

`.env` の `APP_NAME` などを変更します。

```text
APP_NAME=家庭用在庫管理
```

`.env.example` は、新しい環境を作る人向けの設定見本です。アプリ独自の環境変数を追加した場合は `.env.example` も更新してください。ただし秘密情報の実値は書きません。

---

## 4. SQLiteのテーブルを変更する

データモデルに合わせて `app/schema.sql` を変更します。

開発初期でまだ実データがない段階なら、テーブル構成を大きく変更して構いません。

一方、実際の利用を開始した後は既存テーブルを安易に作り直さないでください。保存済みデータを失う可能性があります。

運用開始後は次の流れにします。

```text
DBバックアップ
   ↓
マイグレーションを準備
   ↓
DB変更
   ↓
テスト・動作確認
```

小規模アプリなら `schema_migrations` テーブルと番号付きSQLでも対応できます。規模が大きくなればSQLAlchemy / Alembic等の導入も検討できます。

---

## 5. 業務処理を変更する

現在の `app/services/items.py` がサンプルです。

ここを自分の機能へ置き換えます。

```text
items.py
  list / create / get / toggle / delete
        ↓
equipment.py など
  list / create / get / update / delete / search ...
```

SQLでは、利用者ごとにデータを分離する設計なら `owner_user_id` 等の条件を外さないよう注意してください。

画面側だけで「他人のデータを隠す」のではなく、**DB取得・更新時点で認可する**ことが重要です。

---

## 6. URL・APIを変更する

`app/routes.py` に、自分の画面やAPIを追加・変更します。

たとえば備品管理なら次のような構成が考えられます。

```text
GET  /equipment
POST /equipment
POST /equipment/<id>/update
POST /equipment/<id>/delete
```

JavaScriptからPOST / PUT / PATCH / DELETEなどの更新APIを呼ぶ場合はCSRFトークンを送信します。

```html
<meta name="csrf-token" content="...">
```

```text
X-CSRF-Token: ...
```

理由なく広範囲なCORSを有効にしないでください。

---

## 7. 画面を変更する

主に次を変更します。

```text
app/templates/
app/static/app.css
app/static/app.js
```

まず一覧・登録など最小限の画面を作り、動作確認してから検索、絞り込み、管理画面などを追加すると問題を切り分けやすくなります。

スマートフォンから使うアプリでは、PC画面だけでなくスマートフォン幅でも確認してください。

---

## 8. 利用者・権限をカスタマイズする

初期状態ではTailscaleのログイン利用者をSQLiteの `users` テーブルへ対応付け、localhostでは `.env` のローカルオーナーを利用します。

用途に応じて次を追加できます。

- 管理者 / 一般利用者
- オーナーフラグ
- 複数利用者の共有データ
- 利用者別設定
- 操作履歴（監査ログ）

Tailscaleとアプリの役割は分けて考えます。

```text
Tailscale
  このアプリまで到達してよいか
        ↓
Webアプリ
  この利用者が何を操作してよいか
```

ネットワーク到達制御だけでアプリ内権限を代用しないことが重要です。

---

## 9. テストを自分の機能へ変更する

`tests/` のサンプルテストを、新しい機能へ合わせて変更・追加します。

最低限、次を確認します。

- 正常に登録できる
- 一覧・詳細を取得できる
- 更新できる
- 削除できる
- 不正な入力を拒否できる
- CSRFなしの更新を拒否できる
- 未認証利用者を拒否できる
- 利用者Aが利用者Bのデータを取得・変更できない

ローカルテストの実行方法やCIでの確認方法は [開発・CI・ローカル反映・デプロイ運用](DEVELOPMENT-DEPLOYMENT.md) を参照してください。

---

## 10. 共通基盤を変更するときの注意

次は特別な理由がない限り、削除・弱体化しないことを推奨します。

```text
app/auth.py
app/csrf.py
app/security.py
run.py
```

特に維持したい仕組みは次です。

- Pythonは `127.0.0.1` のみで待ち受ける
- Tailscale Serveを外部接続の入口にする
- Tailscale利用者情報を安全な条件でのみ信用する
- 認証・認可
- CSRF対策
- セキュリティヘッダー
- 利用者ごとのデータ分離

変更が必要な場合は [セキュリティ設計](SECURITY.md) と [アーキテクチャ](ARCHITECTURE.md) を確認してから設計してください。

---

## 11. 実データを扱い始める前にバックアップを決める

SQLiteの実データは通常次にあります。

```text
data/app.db
```

実運用前に最低限、次を決めます。

- バックアップ先
- バックアップ頻度
- 保存世代数
- 復元方法

書き込み中のDBファイルを単純コピーするより、SQLiteのバックアップAPI等を利用する方が安全です。バックアップはGitリポジトリの外へ保存します。

---

## 12. 推奨するカスタマイズ順序

```text
1. 要件・データ項目を決める
      ↓
2. schema.sqlを変更
      ↓
3. servicesの業務処理を変更
      ↓
4. routes / APIを変更
      ↓
5. templates / staticを変更
      ↓
6. testsを変更・追加
      ↓
7. ローカルで動作確認
      ↓
8. GitHubへ反映してCI確認
```

一度に全部作り替えるより、小さな単位でテストしながら進める方が原因を特定しやすくなります。
